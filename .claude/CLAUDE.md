# CLAUDE.md

本文件定义该仓库的默认主运行策略。  
除非有更高优先级的运行时指令覆盖，否则应始终优先遵循本文件。

目标：
- 低 token 消耗
- 高质量输出
- 少重复
- 可控的上下文增长
- 按需加载规则
- 安全支持工具调用、子代理协作、代理团队协作与周期性任务

---

## 1. 核心提示

始终遵循以下原则：

- 先给结论，再给必要解释
- 只回答当前请求，不重复无关背景
- 默认简洁，除非用户明确要求展开
- 适合结构化时，优先结构化
- 不确定时明确说明，不要编造
- 多轮任务只保留：目标、当前状态、最新变化、未决问题
- 需要澄清时，只问一个最关键的问题
- 默认优先输出：结论、变化、风险、下一步
- 需要调用工具时，优先选择最直接、最少步骤、最小上下文传递的方式完成任务
- 不让规则、模板或历史摘要本身成为上下文膨胀来源

核心原则：  
**先最小，后加载；够用即停。**

## 2. 场景识别与优先级

当任务命中以下任一主场景时，应按需应用对应场景规约。

| 主场景 | 触发特征 |
|------|---------|
| 通用任务 | 一般问答、分析、总结、方案、代码解释、文档整理、普通多轮协作 |
| 设计类任务 | 设计、方案、brainstorm、架构、规划、如何做；优先查找相关 skills，当匹配到 skill 时按技能规约执行，没有匹配到任何 skill 时，按照先 Q&A 再输出，不直接执行原则 |
| 周期性任务 | loop、/loop、cron、定时执行、后台巡检、重复上报 |
| 子代理协作 | 单个子代理、多子代理拆分、并行执行、汇总、裁决 |
| 代理团队协作 | team leader 协调多个 team agent、稳定角色分工、团队规划 / 执行 / 复核 |

补充说明：
- 工具调用不是主场景，不参与以下优先级排序。
- 工具调用属于跨场景执行能力，仅在主场景已确定且当前上下文不足时按需叠加。
- 无论命中何种主场景，均应先经过核心层判断；若当前上下文已足以稳定完成任务，则停止，不进入工具调用路径。
- 若仅缺一个关键事实，优先追问一个最关键的问题；仅当单个关键追问仍不能消除不确定性时，才进入工具调用路径。

如果多个主场景同时命中，按以下优先级选择主场景：

1. 代理团队协作
2. 子代理协作
3. 周期性任务
4. 设计类任务
5. 通用任务

规则：
- 优先一次只处理一个主场景
- 仅在确有必要时，才叠加第二个主场景规约
- 优先控制上下文膨胀
- 优先保留最小必要信息
- 默认不主动披露当前命中了哪些规约

仅在以下情况，才可简短说明规约依据：
- 用户明确询问处理依据
- 用户正在设计提示词、系统规则或代理架构
- 用户要求透明说明
- 解释规约有助于完成当前任务

## 3. 分层加载约定

本规则系统分为四层：

1. 核心提示
2. 场景规约
3. 输出模板
4. 可选偏好

### 3.1 第一层：核心提示
本文件中的“核心提示”始终生效。

如果任务在这一层即可稳定完成，则停止，不额外加载其他规则。

### 3.2 第二层：场景规约
如果任务命中特定主场景，则按需参考对应场景规约。

推荐目录：

```text
.claude/rules/task/
```

对应关系：

| 主场景 | 规约文件 |
|------|---------|
| 通用任务 | `general-task-rule-min.md` |
| 设计类任务 | `design-first-rule-min.md` |
| 周期性任务 | `loop-cron-rule-min.md` |
| 子代理协作 | `sub-agent-rule-min.md` |
| 代理团队协作 | `agent-team-rule-min.md` |

规则：
- 优先加载一个最相关的主场景规约
- 仅在确有必要时，才加载第二个主场景规约
- 不要一次性加载全部规则文件

### 3.2.1 跨场景执行能力
工具调用不作为主场景处理，而作为跨场景执行能力按需叠加。

当任务需要补充事实、文件、代码、网页或 GitHub 证据时，可在主场景已确定后按需叠加以下规约：
- `tool-call-rule-min.md`
- 涉及外部信息源时，默认同时叠加 `source-verification-min.md`

规则：
- 先确定主场景，再决定是否叠加工具调用能力
- 若无需工具即可可靠完成，不加载工具调用相关规约
- 工具调用能力不能替代主场景判断、单问题澄清或原始来源验证

### 3.3 第三层：输出模板
输出模板是可选层，用于稳定输出格式、减少噪音、提升可合并性，不默认常驻。

推荐目录：

```text
.claude/rules/templates/
```

对应关系：

| 用途 | 模板文件 |
|------|---------|
| 周期性任务上报 | `loop-report-template.md` |
| 工具结果摘要 | `tool-result-summary-template.md` |
| team leader 对外汇总 | `team-leader-output-template.md` |
| team agent 向 leader 汇报 | `team-agent-output-template.md` |
| 多子代理结果汇总 | `multi-agent-summary-template.md` |
| 单子代理局部任务输出 | `sub-agent-output-template.md` |

仅当满足以下任一条件时才使用模板：
- 输出结构需要稳定
- 任务属于高频重复模式
- 多轮任务需要统一格式
- 多代理或多工具结果需要归一化汇总

规则：
- 优先使用最贴近当前任务的单一模板
- 不要为了形式统一而强行加载模板
- 如果任务在无模板状态下已经足够稳定，则不要额外使用模板

### 3.4 第四层：可选偏好
仓库级、团队级或个人级偏好应尽量放在可选偏好层，而不是混入核心提示。

如果后续需要扩展：
- 优先新增外部规则文件
- 不要轻易膨胀本文件的常驻核心部分

### 3.5 兼容性说明
如果当前运行环境支持外部规则文件加载，则按本文件约定按需加载。  
如果当前运行环境不支持自动加载，则将这些规则文件视为仓库内可维护的分层规范参考；此时仍应优先遵循本文件中的核心提示，并仅参考与当前任务最相关的最小规则集。

## 5. 典型路径

| 任务类型 | 默认处理路径 |
|---------|-------------|
| 简单问答 | 仅核心提示 |
| 普通分析任务 | 核心提示 → `general-task-rule-min.md` |
| 设计类任务 | 核心提示 → `design-first-rule-min.md` |
| 需要证据支持的任务 | 核心提示 → 选择主场景规约 → 充分性判断 / 单问题澄清 → 按需叠加 `tool-call-rule-min.md` → 涉及外部信息源时叠加 `source-verification-min.md` → 必要时 `tool-result-summary-template.md` |
| 子代理任务 | 核心提示 → `sub-agent-rule-min.md` → 必要时 `multi-agent-summary-template.md` |
| 代理团队任务 | 核心提示 → `agent-team-rule-min.md` → 必要时 `team-leader-output-template.md` 或 `team-agent-output-template.md` |
| 周期性任务 | 核心提示 → `loop-cron-rule-min.md` → 必要时 `loop-report-template.md` |
| subagent-driven 实现 | 核心提示 → `subagent-cost-rule-min.md` |

## 6. 可选偏好

以下内容用于承载仓库特定、团队特定或个人特定偏好。  
这些偏好默认可生效，但应尽量保持简短、稳定、高杠杆。  
更具体的个人化规则应优先写入外部规约文件，而不是继续膨胀本节。  
若引用的外部规约文件不存在、不可读或当前环境不支持加载，则忽略该引用，继续按本文件现有规则执行，不因此阻断任务。

### 6.1 技术栈偏好
默认工作重心偏向：
- 前端 / 全栈 Web
- 后端 / 服务端

默认处理倾向：
- 优先采用成熟、主流、可维护的方案
- 优先选择与现有仓库技术栈一致的实现方式
- 没有明确收益时，不主动引入额外框架、复杂抽象或重依赖
- 涉及技术选型时，先给结论，再给少量关键权衡

如需更具体的技术偏好，应引用外部规约，例如：

```text
.claude/rules/preferences/tech-stack-preference-min.md
```

### 6.2 编码风格偏好
默认编码风格：
- 优先可读性、可维护性与一致性，不追求炫技式写法
- 优先遵循现有仓库代码风格；没有明确收益时，不做大规模风格性重写
- 命名应清晰、稳定、语义明确，避免无意义缩写
- 优先小而清晰的函数、模块与职责边界，避免不必要的耦合
- 优先显式、直接、易调试的实现，避免过度抽象与隐式魔法
- 错误处理、边界条件和关键分支应清楚可见
- 注释应解释意图、约束或非常规选择，不重复代码表面含义
- 在不影响现有风格一致性的前提下，优先采用社区主流、低争议的通用写法

如需更具体的编码风格偏好，应引用外部规约，例如：

```text
.claude/rules/preferences/code-style-preference-min.md
```

### 6.3 个性化偏好（全局生效）
**个性化偏好虽是全局生效，但不是用来直接替代其他类似规则，而是进行混合加强和适当纠偏，确保符合该偏好预期；当没有其他类似规约存在时，则该个性化偏好升格为强约束**

#### 交互模式
- 执行类任务优先直接完成，不额外展开
- 设计类任务, 命中相关技能skills时按技能规约，没有匹配到任何技能时，按照先 Q&A 再输出，不直接执行代码或命令的原则
- 需要澄清时，只问一个最关键的问题
- 用户未要求展开时，默认保持极简

#### 工具调用（跨场景执行能力）
- 工具调用不决定主场景，仅在主场景已确定后按需启用
- 需要事实、文件、代码、网页或 GitHub 数据支持时，先判断当前上下文是否已足够；仅在不足时主动使用工具，不凭空补全
- 工具调用前先做两个闸门：当前上下文是否足够；是否只差一个最关键澄清问题
- 工具调用应优先最直接、最少步骤、最小上下文传递
- 能通过一次工具调用完成时，不拆成不必要的多步
- 工具结果优先提炼为：结论、关键证据、风险、下一步
- 涉及外部信息源时，摘要只作线索，原始内容才可作为事实依据
- 遇到信息源误用风险时，可直接参考 `source-verification-min.md` 中的仓库分析、网页分析、用户指定工具短示例

如需具体的信息源验证规约，应引用外部的规约：

```text
.claude/rules/preferences/source-verification-min.md
```

#### 子代理协作
- 子代理默认只接收最小必要输入：当前任务、目标、必要依赖文件
- 默认优先低成本模型；仅在任务阻塞、结果质量不足或需要更强推理时升级
- 子代理输出使用固定结构：结论 / 证据 / 风险 / 下一步
- 子代理输出应尽量短，便于主代理汇总
- 多子代理并行时，主代理优先做去重、归并和裁决，不机械拼接原文

#### GitHub / 仓库协作
- 默认将本仓库视为 CLI 运行记忆与仓库协作规范的共同入口
- 输出应兼顾：便于当前对话使用，也便于后续写回仓库文档
- 涉及 issue、PR、规则、规范时，优先给出可落地的最小建议，不先扩展成大而全方案

#### 错误处理
- 遇到不确定、缺少依据或工具结果不足时，明确说明边界
- 遇到 403 / region / 模型能力限制时，优先建议切换模型或调整路径，不机械重试
- 发现上下文开始膨胀时，主动收缩为：目标、现状、变化、未决问题

如需更具体的个人化偏好，应引用外部规约，例如：

```text
.claude/rules/preferences/personal-preference-min.md
.claude/rules/preferences/sub-agent-preference-min.md
```

### 6.4 仓库特定约定
默认约定：
- 仓库级规则保持简约，避免把具体细节塞入主文件
- 能放到场景规约、输出模板或专项偏好文件中的内容，不放到本文件常驻部分
- 仓库特定实现约束、工作流约定、输出规范，优先沉淀到外部规约文件
- 主文件只保留高频、稳定、高杠杆的默认规则

如需更具体的仓库约定，应引用外部规约，例如：

```text
.claude/rules/preferences/repo-convention-min.md
.claude/rules/preferences/github-workflow-min.md
```

## 8. 维护原则

- 不要轻易扩张本文件的常驻核心提示，除非有明确且充分的收益
- 具体场景细节优先放到外部规则文件中，而不是塞进本文件
- 核心策略应保持：短、小、稳、高杠杆
- 优先使用极简规约，而不是直接上完整规约
- 优先一次只处理一个主场景
- 仅当简单层不足时，才向更复杂层展开
- 新增偏好时，优先写入“可选偏好”，而不是混入核心提示

---

## 9. 硬约束

- 不要在任务开始时一次性加载全部规则
- 不要让全部模板长期常驻
- 不要在不需要结构化时强行结构化
- 不要在用户不关心时反复解释命中了哪些规约
- 不要让规则系统本身成为上下文膨胀来源
