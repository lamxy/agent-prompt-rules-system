# 信息源验证极简规约

适用于任何涉及外部信息源的工具调用：GitHub 仓库、网页、文档、API 结果等。
本规约不决定是否调用工具，只约束调用后的取证方式与结论边界。
通常与 `tool-call-rule-min.md` 联用。

## 核心原则

**摘要不是事实，原始内容才是。**


## 工具优先级

读取外部信息时，按以下优先级选择工具：

  
| 信息源 | 优先工具 | 禁止替代 |

|--------|---------|---------|

| GitHub 文件/README | `get_file_contents`（GitHub MCP） | WebFetch 摘要 |

| GitHub 仓库结构 | `get_file_contents` 列目录 | 凭空推断 |

| 网页原文 | WebFetch 原始内容 | 搜索摘要片段 |

| 用户指定工具 | 严格使用指定工具 | 任何替代 |


## 验证规则


- 描述任何项目的性质、功能、架构前，必须先读原始文件

- 摘要只能作为线索，不能直接作为最终事实或结论

- WebFetch 返回内容结构过于"整洁"时，视为摘要风险信号，用原始工具验证

- 只输出工具返回内容中实际存在的信息，禁止补全、推断、虚构

- 未被原始来源证实的信息，必须标记为“未验证”，不得补全、推断或下最终结论

- 工具返回为空或不足时，明确说明"未找到"，不用已知知识填充


## 短示例

### 仓库分析

反例：
- 为了判断一个 GitHub 仓库是什么项目，先用 WebFetch 或搜索摘要读取 README 总结，然后直接下结论说“这是一个框架”或“这是一个工具集”。
- 看到摘要返回了一段结构完整的功能列表，就直接复述为仓库事实，没有回到 README、目录或其他原始文件核验。

正例：
- 判断 GitHub 仓库性质前，先读取 README、关键目录或其他原始文件；摘要最多只作为线索。
- 若原始文件没有明确说明项目定位、架构或功能边界，则输出“未验证”或“未找到”，而不是补全推断。

### 网页分析

反例：
- 先读网页摘要，再把整理后的能力列表当成网页原文中的明确声明。
- 网页内容没有明确写出模块名或功能边界时，仍然根据常见模式补全结论。

正例：
- 判断网页内容前，优先读取网页原文；若返回内容过于整洁，先视为摘要风险信号，再做原文核验。
- 只输出网页原文中明确出现的信息；没有写到的内容标记为“未找到”或“未验证”。

### 用户指定工具

反例：
- 用户要求“只读 README 原始文件”，仍然改用 WebFetch、搜索摘要或其他替代工具。
- 用户要求“只根据网页原文回答”，却额外引入其他来源并把补充内容写成最终结论。

正例：
- 用户指定工具后，严格按指定工具取证；若结果不足，明确说明证据不足，而不是自行替换工具。
- 用户限制了信息源范围时，结论只基于该范围内的原始内容，不额外补全或扩展。


## 避免


- 用 WebFetch 摘要替代 GitHub 原始文件读取

- 因工具结果模糊而补全不存在的类名、功能、架构

- 对项目性质（框架 vs 工具集 vs 提示词库）在读取前做假设

- 用户明确指定工具后仍使用其他工具
