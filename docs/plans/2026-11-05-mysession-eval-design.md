# mysession-eval 技能設計

日期：2026-11-05　狀態：已過建構者審閱與使用者審閱

## 目的

計畫文件 `docs/plans/2026-10-20-scenario-config-evaluation-plan.md` 3.4「真實專案試用」需要試用資料，用來按 3.5 判定表對場景配置做「通過／調整／移除」判定。本技能取代手填試用日誌：使用者在真實專案裡做完一件事時呼叫它，由 Claude 從會話記錄取得客觀指標、推定主觀項目並寫入日誌；覆盤時由 Claude 匯總、比對、初判，使用者只在關鍵處決策。

**目標是有效評估，不是產出改進項。**「目前配置不錯、未發現需要調整的項目」是合法結論，只要有足夠的樣本與涵蓋面支撐。

## 使用者已決定

1. **主動呼叫**：只在使用者輸入 `/mysession-eval` 時運作。不用 SessionEnd 或其他 hook 自動記錄（避免在非試用專案留痕）。
2. **記錄單位是「一件事」**：使用者做完一件事（一個功能、一次部署、一份 PRD）時呼叫。統計範圍是當前會話中「上一次 `/mysession-eval` 呼叫之後」到這次呼叫為止；本會話沒有前一次呼叫時從會話開頭算。一個會話可以記多筆；同一件事跨多個會話時以任務名稱歸併。
3. **分工：Claude 記錄、統計、比對與評估，使用者只在 Claude 需要時決策**。記錄時只在以下三種情況詢問使用者，其餘直接寫入並回一行摘要：
   - 推定滿意度 ≤ 3（這類分數可能導向調整或移除）；
   - 訊號互相矛盾（例如多次糾正但最後表示滿意）；
   - 這筆可能不該列入判定（中途改需求、網路中斷、任務超出該場景範圍等）。
4. **滿意度由 Claude 推定**，記錄中標明「推定」並寫依據；使用者回答過的標為「使用者確認」。
5. **覆盤時使用者看兩樣**：Claude 提出的「調整／移除」建議，以及推定滿意度的整體分布（分布與使用者感受不符時，修正推定方法）。
6. **使用者最在意的失敗**（反目標見下）：token 成本過高；結論沒用。
7. **不為收益設計**：不硬找問題、不為了「幾次就有收益」降低證據標準。撤回原構想中的「記錄時當場回報問題」，記錄時只記，判斷留到覆盤。
8. **評估深度按配置類型分**（建構者審閱後確認）：
   - 記錄時腳本讀專案 `.claude/`（與專案根的 `CLAUDE.md`、`.mcp.json`），記下當時已安裝的配置清單，並據此判斷場景，不詢問使用者。有了安裝清單，才能看出「裝了卻從不觸發」。
   - skill、agent、MCP、permissions：量化評估，看觸發次數、應觸發未觸發、被拒或要求確認的次數。
   - rules：先補測會話記錄是否記下載入了哪條 rule；有就量化，沒有就降為定性評估。（補測結果：有記錄，量化評估，見「已驗證的前提」）
   - `CLAUDE.md`：只做定性評估，看使用者的糾正內容是否屬於 `CLAUDE.md` 已寫的約定。
9. **判定門檻與基線**（建構者審閱後確認）：
   - 不與階段 1 基線比數字（基線是標準任務，不是真實專案）。3.5 的「干預次數下降」解讀為試用期內前後趨勢。基線只做定性對照：`docs/evaluation/2026-10-baseline.md` 與 `2026-10-final.md` 記錄的已知問題，在真實專案裡是否再出現。
   - 滿意度只用於場景整體的判定，不分攤給單一配置；單一配置只看第 8 條的客觀訊號。
   - 樣本門檻：某配置至少 3 筆相關記錄才提「調整／移除」建議；場景整體至少 10 筆才下判定；不足時寫「尚不能判斷，還差 N 筆」。3 與 10 是建議值、無實證依據，試用後可由使用者調整。
10. **覆盤時機**：多次期中覆盤，最後一次最終覆盤，何時執行都由使用者決定，不固定按週。每次記錄回的一行摘要附上該場景的累積筆數與門檻（例如「backend-dev 已累積 7 筆，場景判定門檻 10 筆」），達標時提示可覆盤；這只是計數，不屬問題回報。
11. **安裝方式同 myplugins**：源碼在本倉庫 `dot_claude/skills/mysession-eval/`，測試後由使用者複製到 `~/.claude/skills/`；腳本命令加入 `sandbox.excludedCommands`（`~` 路徑，與 myplugins 一致）。日誌在 `~/.claude/mysession-eval/`，不進專案與本倉庫。

## 已驗證的前提（2026-11-05，Claude Code 2.1.318）

詳見計畫文件 3.4。

- 當前會話 id：Bash 環境變數 `CLAUDE_CODE_SESSION_ID` 等於 `~/.claude/projects/<專案>/<id>.jsonl` 的檔名（`-p` 與互動模式）；`--resume` 沿用原 id 與檔案，`--fork-session` 換新 id 與新檔案（`-p`）。
- `disable-model-invocation: true` 的 skill 不出現在 `skill_listing` 附件（`-p` 與互動模式），仍可 `/<名稱>` 手動呼叫（`-p`）。常駐成本因此為 0。
- 技能斜線命令在 jsonl 中記為一則 user 訊息，內容含 `<command-name>/<名稱></command-name>`，其後一則 `isMeta: true` 的 user 訊息是載入的 SKILL.md（`-p` 與互動模式格式相同）。切點以此辨識。
- `/compact`：session id 與 jsonl 檔不變，檔中多一行 `type: system`、`subtype: compact_boundary`；壓縮前的 `/mysession-eval` 呼叫仍在檔中，切點可辨識（互動模式實測；另有一份真實會話的自動壓縮記錄也是同一 id 同一檔）。
- `/clear`：換新 session id 與新 jsonl 檔，`/clear` 命令本身記在新檔開頭（互動模式實測）。因此 `/clear` 之後的第一次記錄從新檔開頭算；一件事跨越 `/clear` 時，靠任務名稱歸併。
- path rule 被載入時，jsonl 多一筆 `attachment.type: nested_memory`，內含 rule 路徑；無 `paths` 的 rule 在會話開頭的 `instructions` 附件中（`-p` 實測）。rules 因此可量化評估。限制：本機 2.1.318 實測用 Bash `head`／`cat` 讀符合路徑的檔案時不載入 rule，只有 Read 工具會（2 次觀察，可能與 RTK 改寫有關，未深究；與交接文件記載的 2.1.308 行為不同）。「該載入未載入」的判定要考慮這一點。
- 子代理的會話記錄在 `~/.claude/projects/<專案目錄編碼>/<id>/subagents/agent-*.jsonl`（本機確認存在）。

### 指標對應的 jsonl 欄位（本機最近 150 份會話記錄核對）

| 指標 | 欄位與判斷 |
|---|---|
| 使用者中斷 | user 訊息的 text 內容為 `[Request interrupted by user for tool use]`（可能還有其他變體，解析時以前綴 `[Request interrupted by user` 判斷） |
| 權限拒絕 | `tool_result` 的 `is_error: true`，內容屬以下之一：`... has been denied.`（規則或分類器拒絕）、`File is in a directory that is denied by your permission settings.`（deny 規則）、`Claude requested permissions to use ... but you haven't granted it yet.`（非互動模式未授權） |
| 工具錯誤 | `tool_result` 的 `is_error: true` 且不屬權限拒絕；沙箱的 `Operation not permitted` 歸此類但可另行標示 |
| token | assistant 訊息的 `message.usage`；同一 `message.id` 會拆成多行（最多觀察到 7 行）且每行都帶 usage，必須按 `message.id` 去重 |
| 壓縮 | `type: system`、`subtype: compact_boundary` |

錯誤訊息文字會隨 Claude Code 版本改變；解析規則集中在腳本一處，測試用合成 jsonl 覆蓋上述各類。

## 非目標

- 不自動定期記錄或覆盤，不建排程。
- 不修改任何配置。覆盤只提出建議，改動照本倉庫一般流程由使用者確認後另行實施。
- 不評估 Claude Code 本身或模型能力，只評估本倉庫的場景配置（skill、agent、MCP、rules、permissions、CLAUDE.md）。
- 不跨機器同步日誌。

## 反目標（做了也算失敗）

- 每次記錄或覆盤明顯推高上下文（見「token 預算」）。
- 覆盤給出空泛結論（「整體還行」而無依據），或提出沒有證據支撐的改動建議。
- 為了湊結論在樣本不足時下判定。
- 把會話原文（Claude 回覆、工具輸出）讀進上下文或寫進日誌。
- 日誌或寫回本倉庫的結論含專案原始碼、秘密值、真實專案名稱等可識別內容。

## 流程一：記錄（`/mysession-eval`）

1. **腳本 `extract`**：
   - 讀 `CLAUDE_CODE_SESSION_ID`，定位 `~/.claude/projects/<專案目錄編碼>/<id>.jsonl`。找不到時報錯停止，不退回「取最新 jsonl」。
   - 找出本會話最後一次 `/mysession-eval` 呼叫之前的那一次（即上一個切點），統計兩個切點之間的區段；排除本技能自己的呼叫與其工具活動。
   - 區段內呼叫的子代理，其會話記錄在 `~/.claude/projects/<專案目錄編碼>/<id>/subagents/agent-*.jsonl`（2026-11-05 在本機確認存在），其工具、MCP、權限拒絕與 token 一併計入，並與主會話分開標示。（建構者審閱後的 Claude 決定）
   - 讀專案已安裝的配置清單（「使用者已決定」第 8 條）並判斷場景。
   - 輸出精簡 JSON 摘要給 Claude，至少含：區段起訖時間、輪數；skill（含斜線命令與模型自動觸發的 `Skill` 工具呼叫）、agent、MCP 工具的呼叫次數；權限拒絕次數與被拒工具；工具錯誤次數；使用者中斷次數；token 用量（取自記錄中的 usage 欄位）；使用者訊息清單（每則截斷到固定長度，去除系統注入內容）。
2. **Claude 推定**：只根據摘要（含截斷後的使用者訊息）判斷：任務名稱（與近期記錄相近時歸為延續）、完成狀態（已完成／未完成／中斷）、干預次數（糾正與新需求分開）、推定滿意度與依據、是否列入判定、一兩句備註。
3. **詢問或直接寫入**：命中「使用者已決定」第 3 條三種情況之一時，一次列出問題請使用者回答；否則直接寫入。
（2026-11-05 補）使用者決定這段不記錄時，技能改執行 `skip` 子命令：不寫日誌，只作為下次記錄的切點，避免使用者的回答被算進下一段。

4. **腳本 `append`**：Claude 以參數或標準輸入把推定結果交給腳本，腳本合併客觀指標後追加到日誌，回一行摘要（含該場景累積筆數與門檻，見「使用者已決定」第 10 條）。

## 流程二：覆盤（`/mysession-eval review [場景]`）

覆盤分兩種，由使用者呼叫時指定（參數形式留給建構者）：

- **期中覆盤**（可多次）：只對達到樣本門檻的配置給建議，結論標「階段性」；使用者決定是否當場調整配置；不寫回 `2026-10-final.md`。
- **最終覆盤**（試用結束時一次）：涵蓋全部資料，結論去識別化後寫回本倉庫（見第 4 步）。

**配置中途被改**：期中覆盤後可能調整配置，之後的記錄就是用新版配置做的。日誌每筆記下各已安裝配置檔的內容指紋（hash）。覆盤遇到同一配置有前後兩版時分開計算；改動後的樣本不足時照實寫「改動後樣本不足，尚不能判斷」，不與改動前的資料混算。

1. **腳本 `summarize`**：讀日誌，按場景與配置項（及其版本指紋）預先匯總（合併同一任務跨會話的筆數、各配置項觸發次數、權限拒絕分布、推定滿意度分布、干預次數隨時間的變化），只把匯總交給 Claude。
2. **Claude 判定**：讀 `references/review.md`，按 3.5 判定表對每個有足夠樣本的配置項給出初判。
   - 建議「調整／移除」必須指向具體檔案與改法，並附依據的筆數。
   - 證據不足的現象標「觀察中」，不推成建議。
   - 樣本不足的配置項明說「尚不能判斷」，寫出差多少。
   - 沒有發現問題時照實寫，並列出看了哪些面向、各多少筆。
3. **使用者決策**：使用者看「調整／移除」建議與推定滿意度分布，決定採納與否。
4. **寫回（只限最終覆盤）**：結論去識別化後寫入 `docs/evaluation/2026-10-final.md` 的試用章節（經使用者確認後提交，照本倉庫提交流程）。

## 日誌欄位

每筆至少含：記錄時間、session id、區段起訖、專案目錄名、場景、已安裝配置清單（含各配置檔內容指紋）、任務名稱、完成狀態、客觀指標（流程一第 1 步各項）、干預次數、滿意度與其來源（推定／使用者確認）、推定依據、是否列入判定與理由、備註。另含 `schema` 版本號，日後改欄位時舊資料可辨識。

日誌不存使用者訊息原文；推定依據與備註用 Claude 的概述，不引用原文。

日誌只在本機，所以直接記專案目錄名；寫回本倉庫時才換成「場景＋序號」（例如 `backend-dev-1`）。（Claude 決定）

## 與計畫文件的關係

本設計取代計畫文件 3.4「初步設計（未確認）」。其中「每次記錄約 3～4k」是加入「Claude 讀使用者訊息」之前的估計，以本文件的 token 預算為準。（Claude 決定）

## token 預算

| 動作 | 目標上限（估計，未實測） |
|---|---|
| 常駐 | 0（已驗證） |
| 每次記錄 | 約 8k（含 SKILL.md、腳本輸出、推定與寫入） |
| 每次覆盤 | 約 12k |

實作完成後用 API usage 實測。

2026-11-05 端到端實測（Claude Code 2.1.318，臨時專案放 backend-dev 的 `CLAUDE.md` 與 6 個 agent，互動模式；以呼叫前最後一次 API 請求的上下文量對比技能執行結束時的上下文量加輸出，屬近似值）：

| 動作 | 上下文增加 |
|---|---|
| 記錄（無詢問） | 約 2.8k |
| 記錄（含一次詢問） | 約 4.7k |
| 期中覆盤（2 筆記錄） | 約 8.9k |

均在預算內。小會話、記錄少；長會話與記錄多時的 `extract`、`summarize` 輸出量未實測（`extract` 已限制使用者訊息合計 3000 字、配置清單只列種類與名稱）。

同次實測確認：本次 `/mysession-eval` 呼叫在腳本執行前已寫入會話記錄（切點取得正確）；第二筆區段從第一筆 `append` 之後開始；`review` 呼叫不當切點；場景判為 `backend-dev`；日誌不含使用者原文。超出時刪減功能或縮短輸入（例如使用者訊息截斷長度），不提高預算；預算本身要調整時由使用者決定。
