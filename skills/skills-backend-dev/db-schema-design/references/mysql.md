# MySQL 设计参考

`.claude/rules/database/mysql.md` 的条目理由与补充说明。

## 建表

| 规则 | 理由 |
|---|---|
| 自增 `bigint` 主键 | InnoDB 是索引组织表，自增主键让新数据顺序追加到末尾，避免页分裂；`int` 上限约 21 亿（无符号约 43 亿），大表会耗尽，`bigint` 与 Go 的 `int64` / `uint64` 对应 |
| `updated_at` 自动更新并建索引 | 用于增量同步、数据抽取和排查问题，由数据库维护，业务代码不需要写 |
| `utf8mb4` | MySQL 的 `utf8` 实际是 `utf8mb3`，最多 3 字节，存不了 emoji；`utf8mb4` 才对应 Go 字符串的 UTF-8 |
| `ROW_FORMAT=DYNAMIC` | 索引键前缀上限 3072 字节；`COMPACT` 只有 767 字节 |
| 不用外键 | 关联约束放在应用层，便于分库分表和在线变更，避免级联锁；代价是要在设计文档标明全部关联关系，并定期跑孤儿记录检查：`SELECT c.id FROM child c LEFT JOIN parent p ON p.id = c.parent_id WHERE p.id IS NULL`，结果应为 0 行 |
| 对外编号与自增 `id` 分开 | 自增 `id` 会泄露业务量（`order_id=1523` 等于公开了订单总数），也能被遍历猜出他人的数据；对外用 `order_no VARCHAR(32)` 加唯一索引，内容不可预测。代价：utf8mb4 的 `VARCHAR(32)` 索引键长 130 字节，是 `BIGINT` 的 16 倍，单号生成在峰值下不能重复，外部传入的编号要在应用层映射成 `id` |
| 自增主键的代价 | 写入前拿不到 `id`；分库分表后各分片的自增值会冲突，届时改用号段或雪花算法，在 ADR 中与「暂不分表」的决策互相引用 |
| 单表不超过 40 个字段 | InnoDB 页为 16KB；行越小，一页容纳的行越多，读取同样行数所需的 I/O 越少 |
| 不先 `DROP` 后 `CREATE` | 在已有数据的环境执行会直接丢失数据 |

GORM 的 `AutoMigrate` 默认会创建外键，即使只在开发环境使用，也要设 `DisableForeignKeyConstraintWhenMigrating: true`。

## 字段

| 规则 | 理由 |
|---|---|
| `NOT NULL` + 默认值 | `NULL` 参与拼接结果为 `NULL`，`COUNT(col)` 不计 `NULL`，可空列的索引还要额外存储标记；Go 侧也省去 `sql.NullString` 之类的处理 |
| 「没有」用约定值 | 可选关联 id 用 `0`（如顶层分类 `parent_id = 0`、未用券 `coupon_id = 0`），尚未发生的时间用 `'1970-01-01 00:00:00'`，门槛类数值用 `0` 表示无门槛。不能用 `'0000-00-00'`，严格模式（`NO_ZERO_DATE`）会拒绝。约定值要写进 `COMMENT`，查询时按约定值判断，例如 `WHERE paid_at > '1970-01-01'`。用 `0` 表示无父节点时，自连接查父记录必须用 `LEFT JOIN`，否则顶层记录全部消失 |
| `NULL` 例外 | 只在约定值会造成歧义时使用，并在 `COMMENT` 和 ADR 写明理由。可空列上的 `NOT IN (子查询)` 只要子查询里有一个 `NULL`，结果就是 0 行（三值逻辑），实测正确结果应为约 100 万行；改用 `NOT EXISTS`。`= NULL`、`!= NULL` 不报错但永远不成立 |
| 状态用 `TINYINT UNSIGNED` | 状态值一定会增加，`ENUM` 加值要在大表上做 DDL；数据库约束不了合法值（写入 `status = 99` 不会报错），所以 `COMMENT` 要列全取值，并与应用层枚举同步维护。设计前先确认状态机语义，需求里常有互相冲突的流转描述 |
| 标识类字段用 `VARCHAR` | 手机号用数字会丢失前导零和国家码。字符串列与数字比较时，MySQL 把列值转成数字，实测 `WHERE phone = 13000000001`（不带引号）为 `type: ALL`，索引失效；反方向 `WHERE user_id = '500'` 是转换常量，仍能走索引 |
| 主表不放 `TEXT` / `BLOB` | 大对象存在行外，读取要额外 I/O，占用 buffer pool，并拖慢主从复制 |
| `VARCHAR` 不超过 2000 | 索引长度按定义长度计算，而非实际长度 |
| 不改字段类型、不删字段 | 这类变更通常要重建表；在线变更需借助 gh-ost、pt-online-schema-change 或 8.0 的 `INSTANT` 算法，并评估锁表时间 |
| `DECIMAL` 存金额 | `FLOAT` / `DOUBLE` 是近似值，有精度损失；Go 侧用 `shopspring/decimal` 等类型或以最小单位存整数 |
| `TINYINT` 代替 `ENUM` | `ENUM` 增加取值要改表结构，排序按定义顺序而非字面值 |
| `datetime` 代替 `timestamp` | `timestamp` 上限为 2038-01-19；`datetime` 范围是 1000～9999 年。注意 `datetime` 不带时区，统一约定存 UTC 或固定时区。需要毫秒时用 `datetime(3)`，存储与索引键宽 7 字节（基础 5 字节，每 2 位小数加 1） |
| 日期范围用半开区间 | 实测 `WHERE DATE(created_at) = ?` 扫描约 99 万行，`created_at >= ? AND created_at < ?` 只扫 1,570 行；`BETWEEN ... AND '...-31'` 还会漏掉最后一天的非零点数据 |
| 金额对账用容差 | 冗余总额与明细加总比较时用 `ABS(a - b) > 0.01`，不用 `<>`，避免加总后的进位差异被误判 |

## 软删除

- `is_deleted TINYINT NOT NULL DEFAULT 0` 最简单，代价是不知道何时删除；排查时可参考 `updated_at`，但它也会被其他更新覆盖。
- 需要删除时间时，加 `deleted_at datetime NOT NULL DEFAULT '1970-01-01 00:00:00'`，未删除的行保持约定值。
- 表上有业务唯一键（如手机号）时，已删除的行仍占着唯一值，同一手机号无法重新注册。`UNIQUE (phone, is_deleted)` 只允许删除一次；改用 `UNIQUE (phone, deleted_at)`：未删除的行共用约定值，因此仍互斥，已删除的行各有不同的删除时间，可以并存。
- 已删除的行仍在索引里。删除占比高时，把删除标记放进常用的组合索引，或定期归档；占比低（几个百分点）不必处理。
- 「下架」与「删除」是两个维度：下架看业务状态字段，删除看软删除标记，不要合并成一个字段。

以上软删除方案是通用做法，未在教学库中实测。

## 反正规化

先做到第三范式，再按需求刻意退回。判断是否冗余只问一句：**这个字段变了，历史记录该不该跟着变？** 该跟着变就关联查询，不该跟着变就做快照。例如订单里冗余用户昵称是错的，昵称改了，订单不需要保留旧昵称；冗余下单时的单价是对的，严格第三范式会让历史订单金额随调价变化。

| | 快照型 | 冗余计算型 |
|---|---|---|
| 例子 | `price_snapshot`、收件地址快照 | `orders.total_amount`、`products.sales_count`、`order_items.product_id` |
| 会不一致吗 | 不会，历史不再改变 | 会 |
| 维护方式 | 不需要 | 与源数据在同一事务内更新，另设校验 SQL 兜底 |

- 每处冗余都在设计文档写明类型与维护方式，否则日后会被当成 bug「修掉」。
- 校验 SQL 示例（实测在 250 万行明细上全量运行需十几到几十秒，生产环境只校验最近 N 天、按 `id % 100` 抽样，或在夜间异步运行并告警）：

```sql
SELECT o.id, o.total_amount, SUM(oi.subtotal) AS items_sum
FROM orders o JOIN order_items oi ON oi.order_id = o.id
GROUP BY o.id, o.total_amount
HAVING ABS(o.total_amount - SUM(oi.subtotal)) > 0.01;
```

- 快照名称可能因商品改名而不同，统计时用 `ANY_VALUE()` 或 `MAX()` 取名称，不要把快照名放进 `GROUP BY`，否则改过名的商品会被拆成多行。
- 冗余的代价要量化，例如「96 B/行 × 1900 万行 × 1.3 ≈ 2.3 GB」，不写「增加了一些空间」。

## 索引

### 原理

- 二级索引的叶子节点存的是索引列加主键，主键越短，二级索引越小；只查主键时，任何二级索引都是覆盖索引。
- 组合索引 `(a, b, c)` 的条目按 `a → b → c` 逐列排序。`a = ?` 切出的连续区间内 `b` 整体有序；`a > ?` 跨过多个 `a` 值，`b` 只在每个 `a` 值内部有序，整体无序。由此得出：
  - 最左前缀：`WHERE` 只用到后面的列时，不能用索引定位。
  - 范围截断：遇到第一个范围条件后，后续列不再参与定位，只能做索引下推过滤（`Using index condition`）。
  - ESR：等值（Equality）在前，排序（Sort）次之，范围（Range）在后。MongoDB 的索引也是按键有序的树，因此遵循同一原则。

### 列顺序（ESR）的实测依据

| 索引 | 查询 | 结果 |
|---|---|---|
| `(user_id, status, created_at)` | `WHERE user_id=? AND status=? ORDER BY created_at DESC` | `ref`，`key_len 9`，`Backward index scan`，无 `filesort`：排序列不计入 `key_len`，但免去了排序 |
| `(status, total_amount)` | `WHERE status=1 AND total_amount>8000 ORDER BY total_amount DESC` | `range`，无 `filesort`：范围就作用在排序列本身 |
| 范围列与排序列不同 | `WHERE user_id=? AND created_at 范围 ORDER BY total_amount DESC` | 仍有 `filesort`：一个索引无法同时优化另一列的范围和排序 |
| `(user_id, created_at, status)` | `WHERE user_id=? AND created_at>? AND status=?` | `key_len 15`，`status` 只做下推，不参与定位 |
| `(user_id, status, created_at)` | `WHERE user_id=? AND created_at>?` | `key_len 8`，中间列缺席同样截断 |
| `(created_at, status)` | `WHERE created_at 范围 GROUP BY status` | `range`，`Using index; Using temporary`：范围之后的列分组仍要临时表 |

范围列与排序列不同时，二选一：范围列紧跟等值列，扫描行数少但要排序；排序列紧跟等值列，免排序但扫描行数多。带 `LIMIT` 的分页列表通常选后者，范围很窄、结果很少时选前者。取舍写进设计文档。`GROUP BY` 能免临时表的情况只有一种：分组列紧跟等值列，或者就是索引首列。

### 选择性

- 看「每个值平均对应多少行」，不只看比值。`status` 只有 4 个值、其中一个占 70%，单独建索引后实测仍是 `type: ALL`，优化器放弃了索引；`order_items.sku_id` 选择性只有 0.0006，但每个值约对应 1,664 行，只占全表 0.07%，值得建。
- 低选择性列可以放在高选择性列后面做组合索引的后续列。
- 判断顺序：先看表大小（几千行以内的小表不需要二级索引），再看选择性，最后看查询频率。
- 分布不均的低选择性列常出现在 `WHERE` 中时，用直方图代替索引：`ANALYZE TABLE t UPDATE HISTOGRAM ON status;`。没有直方图时，优化器对等值条件的 `filtered` 默认猜 10%，实测预估 99,136 行，实际 70 万行。直方图不随写入更新，要定期 `ANALYZE`。

### 覆盖、冗余与代价

- 覆盖索引对「范围查询 + 大量回表」最有效，只为高频、字段固定的查询建。不要把宽列放进去：把 `order_no`（130 字节）加入覆盖索引，估算索引会膨胀约 6 倍。
- 冗余索引（已有 `(a,b,c)` 再建 `(a)` 或 `(a,b)`）只增加写入成本。同样的列换个顺序不等价，但为了「保险」两种顺序都建，实测各占约 30 MB。
- 实测 4 个二级索引让插入慢 3～4 倍；更新索引列等于先删后插。频繁更新的列慎建索引。
- 唯一索引写入较慢（用不了 change buffer），但关键的唯一性仍要由它保证；「先查再插」在并发下会穿透。唯一约束建立在稳定的业务规则上，例如允许支付失败后重试，`payments.order_id` 就不能唯一。
- 前缀索引不适合需要排序、分组或覆盖的场景。前缀长度取选择性曲线变平的拐点：比较 `COUNT(DISTINCT LEFT(col, N)) / COUNT(*)`，实测 15 个字符时为 0.96，到 20 个字符只高 4%，宽度却多 33%。URL 这类前缀高度重复的字段改为存哈希列并建索引。
- 全表聚合（不限时间范围的排行、汇总）索引救不了，只能预计算、增量维护或交给分析库。

### 读执行计划

- 先看四列：`type`、`key`、`rows`、`Extra`。`Using filesort`、`Using temporary` 是红灯。
- `type: index` 是扫描整个索引，行数并没有减少；判断索引是否生效看 `rows` 有没有数量级的下降。
- `possible_keys` 有值而 `key` 为 `NULL`，是优化器主动放弃；`possible_keys` 为 `NULL`，才是真的没有可用索引。
- `key_len` 判断组合索引用到了几列。常见宽度：`BIGINT` 8、`INT` 4、`TINYINT` 1、`datetime(3)` 7、utf8mb4 `VARCHAR(n)` 为 4n+2，可空列再加 1。
- `rows` 是预估值，只看数量级；怀疑预估偏差时用 `EXPLAIN ANALYZE`（会真正执行语句，不要对写语句使用）。
- 8.0.13 起可能出现 `Using index for skip scan`：缺少最左列时仍能部分使用索引，但查询含 `GROUP BY` 或 `DISTINCT` 时不适用。
- `OR` 两边列都有索引时，`index_merge` 可能比手动改写成 `UNION` 更好，`UNION` 会多出临时表。

## SQL

| 规则 | 理由 |
|---|---|
| 不用 `SELECT *` | 无法使用覆盖索引，读取多余数据；表结构变化时还可能让扫描结果与结构体错位 |
| `WHERE` 字段不套函数、类型一致 | 函数和隐式类型转换都会让索引失效（8.0 可以建函数索引，但先考虑改写查询） |
| 不用前导通配符 `LIKE` | 不符合最左匹配，退化为全表扫描；需要全文检索时用 Elasticsearch 或全文索引 |
| 控制单条语句影响行数 | 主从复制在事务提交后才发送到从库，大事务直接转化为复制延迟；回滚耗时也与事务大小成正比 |
| 关联不超过两张表、少用子查询 | MySQL 的关联算法与优化器对复杂 SQL 支持有限，拆成多条简单查询更可预期 |
| 不用 hint | 数据分布变化后，固定的执行计划可能变成最差的计划 |
| 深分页改游标 | `LIMIT 100000,10` 要扫描并丢弃前 100000 行；`WHERE id > ? ORDER BY id LIMIT 10` 直接定位。排序键不唯一时加主键作决胜列，`WHERE (created_at, id) > (?, ?)`，否则用 `>` 会漏行、用 `>=` 会重复。必须跳页的后台查询用延迟关联：子查询只取 `id`（走覆盖索引），外层只回表一页的行数 |
| 统计语句走从库 | 大范围 `COUNT`、`SUM` 占用主库 I/O 与 buffer pool，影响在线写入 |
| `READ COMMITTED` | 相比默认的 `REPEATABLE READ` 减少间隙锁，降低死锁概率；需要可重复读的逻辑在应用层显式加锁 |
| 写操作幂等 | 网络超时后的重试、消息重复投递都会再次执行写操作；用唯一键、`INSERT ... ON DUPLICATE KEY UPDATE` 或带状态条件的 `UPDATE ... WHERE status = ?` 防止重复 |
| `UNION ALL` 优先 | `UNION` 会额外去重排序，确定没有重复时用 `UNION ALL` |

SQL 写法上更多有实测数据的陷阱，见 `sql-pitfalls.md`。

## 容量预估

```
单行字节 ≈ 各字段宽度之和 + InnoDB 隐藏列约 20 B
单表数据 ≈ 年增行数 × 单行字节 × 年数 × 膨胀系数（1.2～1.5）
单个索引 ≈ (索引列宽度 + 主键 8 B) × 行数 × 1.3
总空间   = 数据 + 全部索引
```

- 索引空间必须单独算：实测 `orders` 建 5 个索引后，数据 126.7 MB，索引 189.5 MB，索引比数据还大。索引公式经实测验证，`(user_id, status, created_at)` 在 100 万行上估算约 31 MB，与实测相符。
- `VARCHAR` 按实际平均长度估算，不按声明长度：ASCII 每字符 1 B，中文 3 B，emoji 4 B，另加 1～2 B 长度前缀；可能为空的字段按填写率加权。按声明长度估算会把 `orders` 的单行宽度高估约 2.6 倍。
- 购物车这类流动数据要定期清理，不按累计量估算。
- 隐藏列 20 B、膨胀系数、索引系数 1.3 都是经验默认值，项目可按实测调整。

## 演进策略

- 「现在慢」多半只是缺索引，不要误判为「该分表」。
- 分表前依次穷尽：补索引 → 冷热分离（归档）→ 读写分离 → 缓存 → 垂直拆分。
- 同时满足以下条件才考虑分表：单表超过约 2000 万行或 20 GB（经验默认值，项目可调整）、已穷尽索引优化、已做冷热分离。达到门槛的 70% 时启动评估。
- 分表的代价：跨分片聚合、分页排序变复杂、分布式事务、需要路由中间件，还要结合团队规模和工期判断。
- 归档方案要回答四个问题：
  1. 哪些表归档：流动数据直接定期删除，量小的维度表不归档。
  2. 保留期多长：按不同需求分别设定，订单与支付的保留期可能不同，不能整组一起搬。
  3. 归档后怎么访问：归档表与主表同结构、按时间路由，或用 `PARTITION BY RANGE`。
  4. 怎么执行：分批进行，先写入归档表再删除，失败有补偿。
- 收集需求时问清已知的下一期需求，在设计文档中写明为下一期预留了什么。

## MySQL 5.7 与 8.0 的差异

| 主题 | 5.7 | 8.0 |
|---|---|---|
| DDL | 不是原子操作，失败后可能残留中间状态，无法回滚 | 原子 DDL，但仍不在事务中回滚，变更前先备份 |
| 加列 | 需要重建或在线复制 | `ALGORITHM=INSTANT` 可秒级加列（不能用 `AFTER` 指定位置时才最快，8.0.29 起支持任意位置但仍建议追加） |
| 函数索引 | 不支持，`WHERE` 中对列使用函数必然全表扫描 | 支持函数索引（8.0.13+） |
| 多个 `ALTER` | 每次都要锁表或复制，必须合并 | 仍建议合并，减少元数据锁次数 |
| 默认字符集 | `latin1` | `utf8mb4` |
| 保留字 | — | 新增 `RANK`、`ROW_NUMBER`、`RANGE`、`SYSTEM`、`WINDOW` 等，5.7 能用的字段名升级后会报语法错误，错误位置指向保留字**后面**的 token。命名时绕开（如 `sort_order`），不靠全表加反引号；用 `INFORMATION_SCHEMA.KEYWORDS` 与 `COLUMNS` 关联自查 |
