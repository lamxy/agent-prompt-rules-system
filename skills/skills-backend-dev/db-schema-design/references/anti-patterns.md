# 反面案例

数据库设计评审中反复出现的错误。评审他人的设计或自查时逐条对照。标「实测」的条目有 MySQL 8.0 执行计划或耗时数据，其余是评审经验。

## 概念与逻辑模型

| 错误 | 为什么错 | 正确做法 |
|---|---|---|
| 把关系当实体，或漏掉多对多的关联表 | 「订单买多个商品」被建成 `orders` 与 `products` 两张表，数量和成交价没有地方放 | 多对多必须有关联表；关联表往往有自己的属性，本身就是实体 |
| 只从界面反推表结构 | 界面上看不到的实体会被漏掉，例如一次付款对应多张订单时需要的支付单 | 把下单、支付、发货、退款、对账逐环走一遍；资金相关的表结构优先确认 |
| 快照需求没落实 | 订单金额用商品现价关联计算，调价后历史订单全错 | 需求里出现「当时的」「不能跟着变」「历史要能查到」，就做快照字段 |
| 冗余用户昵称等「该跟着变」的字段 | 昵称改了订单里还是旧值，又没有人维护 | 先问「它变了，历史该不该跟着变」，该变就关联查询 |
| 冗余计算字段没有维护方案 | `total_amount` 与明细加总逐渐不一致，没人发现 | 同一事务内更新，另写校验 SQL 定期跑 |
| 可单独查询、修改的子数据塞进 JSON | 无法按其中的字段建索引、校验和局部更新；日后被迫拆表时迁移困难，`case-ai-platform.md` 的拆表迁移只处理了数组长度为 1 的记录，其余静默丢失 | 独立建表，例如用户的多个收货地址、版本支持的平台 |
| 用文本业务键或多列组合关联父表 | 每张子表都带 `(code, version)` 两个字符串列，索引变宽；业务键可改时要级联改写全部子表 | 子表存父表 `bigint id`，业务键只留在父表；见 `case-ai-platform.md` |
| 分类等维度用自由文本，并复制到多张表 | 同一分类出现多种拼写，按文本相等匹配的授权、分派逻辑失效；值已复制到多表，清理代价大到被迫放弃 | 建字典表，各表存 `category_id` |
| 同一实体的引用在各表类型、命名不一致 | 用户引用有的叫 `*_uid`、有的是 `ref` + `ref_type`，版本有的叫 `version`、有的叫 `plugin_version`；关联和孤儿检查都容易写错 | 同一实体全库统一为 `<实体>_id bigint` |
| 层级固定写死 | 需求说「以后可能加层级」，却建了一级、二级、三级三张表 | 自参照 `parent_id` |
| 状态机语义没确认就建状态字段 | 需求里「签收即完成」与「完成 7 天后自动确认」互相冲突，上线后才发现状态不够用 | 先画状态流转并和需求方确认 |

## 索引

| 错误 | 为什么错 | 正确做法 |
|---|---|---|
| 以低选择性的 `status` 开头建多个索引（实测） | `status` 4 个值、其中一个占 70%，单独索引实测仍是全表扫描；放在最左，后面的列也难以发挥作用 | 低选择性列不放最左，接在高选择性列之后 |
| 漏建「按父查子」的索引（实测） | `WHERE order_id=?` 从扫描约 242 万行到 5 行，差了五个数量级 | 每张子表的父 id 字段都检查一遍有没有对应的查询 |
| 分组列放最左、范围列放后（实测） | 销售排行用 `(sku_id, created_at)` 比不建索引慢 20 倍：无法按时间定位，只能扫描整个索引并逐行回表 | 范围列在前定位，聚合用到的列放进覆盖索引；见 `case-ecommerce.md` |
| 以为范围列之后的列还能免排序或免临时表（实测） | `(created_at, status)` 配合 `WHERE created_at 范围 GROUP BY status`，实测仍有 `Using temporary` | 按 ESR 排列；范围列与排序、分组列不同时写明取舍 |
| 报表口径没定就建索引 | 「支付成功率」若按结果时间统计，要写成 `paid_at 范围 OR failed_at 范围`，跨两列的 `OR` 用不好索引 | 先和需求方定口径（如按发起时间 `created_at`），再设计索引 |
| 为「保险」建同列不同序的索引（实测） | 每个约占 30 MB，只增加写入成本 | 每个索引都对应一条写明的查询，对应不上的不建 |
| 设计文档与 DDL 不一致 | 文档写普通索引，DDL 是唯一索引（或反过来）；唯一性没有由数据库保证 | 文档的索引类型、名称与 DDL 逐一核对 |
| 改了索引字段没改名 | 字段已改为 `(created_at, status)`，名称还叫 `idx_..._fat_sts` | 名称反映字段，随字段改名 |
| 游标分页的排序键不唯一 | 同一时间戳的多行在翻页时漏掉或重复 | 加主键作决胜列 |

## 字段

| 错误 | 为什么错 | 正确做法 |
|---|---|---|
| 手机号用数字类型，或比较时不带引号（实测） | 丢失前导零；`WHERE phone = 13000000001` 让索引失效，实测全表扫描 | `VARCHAR`，比较值带引号 |
| 用 MySQL 8.0 保留字命名 | `rank` 等字段在 5.7 可用，升级后报语法错误，而且错误位置指向后一个 token，不易发现 | 命名时绕开保留字 |
| 唯一约束建在「目前数据刚好唯一」上 | `payments.order_id` 加唯一后，支付失败无法重试 | 唯一约束只建在稳定的业务规则上 |
| 主键用业务值、随机 UUID 或文本，且多种并存 | 见「从 PostgreSQL 设计迁移到 MySQL」；业务值主键一旦要改，等于改主键 | 每张表自增 `bigint id` 主键 |
| 加 `NOT NULL` 列时用随机值或魔法字符串回填 | 用随机 UUID 填引用字段，它从一开始就指向不存在的记录，且与真实引用无法区分；`'legacy'` 之类的占位串混进统计 | 可选关联填约定值 `0` 并写进 `COMMENT`；需要区分历史数据时加 `is_legacy TINYINT NOT NULL DEFAULT 0` |

## 容量与演进

| 错误 | 为什么错 | 正确做法 |
|---|---|---|
| `VARCHAR` 按声明长度估算 | `orders` 单行宽度高估约 2.6 倍 | 按实际平均长度估算 |
| 漏算索引空间（实测） | 5 个索引后索引 189.5 MB，比 126.7 MB 的数据还大 | 每个索引单独估算 |
| 流动数据按累计量估算 | 购物车被估成千万级 | 定期清理，按保留期估算 |
| 分表门槛写错单位，或「分表前先做什么」只写「同上」 | 演进策略无法执行 | 写明门槛数值与单位、分表前的手段和顺序 |
| 归档只有原则没有方案 | 「定期归档历史数据」无法执行 | 回答四个问题：哪些表、保留期、归档后怎么访问、怎么执行 |
| 拆表重构后旧字段不下线 | 新旧字段并存成为双重数据源，哪一处是真实来源只能看代码 | 设计文档列出下线计划：先停写，再停读，最后删列 |
| 修改已发布的 migration，或用条件式 DDL（`IF EXISTS` 判断列类型再分支）兼容未知状态 | 各环境的结构不再一致，后续 migration 只能越写越防御 | 已发布的 migration 不改，修正写成新的 migration |

## 交付文档

| 错误 | 正确做法 |
|---|---|
| 「不涵盖范围」里混进技术约束 | 业务范围与技术约束分开写 |
| ADR 只写决定，代价没量化或引用出处有误 | 五段式：背景 / 选项 / 决定 / 理由 / 代价，代价给数字和缓解措施 |
| 待确认问题没有优先级 | 按影响排序：影响表结构 > 影响索引 > 影响应用逻辑 |
| 变更历史只写「更新」 | 写清改了哪张表、哪个字段或索引、为什么 |
