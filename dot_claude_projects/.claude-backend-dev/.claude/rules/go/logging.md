# 日志

使用项目统一的结构化 logger（如 `log/slog`、zap、zerolog），输出 JSON，一行一条。

## 级别

| 级别 | 用途 |
|---|---|
| `DEBUG` | 开发排查；生产环境不输出 |
| `INFO` | 启动参数与启动完成、配置加载、业务状态变化、核心流程的关键节点、服务之间的调用 |
| `WARN` | 结果与预期不符但可继续：用户输入参数错误、外部返回码异常、可恢复的降级 |
| `ERROR` | 程序逻辑错误与未处理的异常；会触发告警，可预期的业务失败不用 `ERROR` |

上线初期用 `WARN` 观察业务行为时，注意输出量，事后调回。

## 字段

每条日志包含：`timestamp`、`level`、`service`、`message`，以及请求链路的 `trace_id`、`span_id`。按需补充：

- `type`：`ACCESS`（接口访问）或 `EVENT`（业务事件）
- `biz_tag`：业务标签，如 `order.place`，同一业务流程使用同一个标签
- `biz_id`：业务主键，如订单号
- `url`、`cost_ms`：接口路径与耗时
- `alert`：需要告警的 `INFO` / `WARN` 日志加上该字段，由告警规则匹配

字段名在项目内统一，用 `snake_case`。

## 内容

- 接口访问日志由中间件统一输出，不在每个 handler 里重复写；未捕获的 panic 由中间件恢复并记录 `ERROR`。
- 与外部系统交互（回调、对账、文件交换）时记录原始请求与响应的摘要；需要重发的失败数据存入数据库，而不是只写在日志里。
- 日志信息要完整，能单独看懂：写明对象、动作和关键参数，不写「处理失败」这类无上下文的信息。
- 不输出密码、token、完整的身份证号或银行卡号等敏感信息，必要时脱敏。
- 服务输出到 stdout，由采集器（Filebeat、Fluent Bit 等）收集；必须写本地文件时按天切分，文件名为 `<级别>_<日期>.log`，例如 `error_20261021.log`。
