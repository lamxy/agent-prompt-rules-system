# MySQL 设计参考

`.claude/rules/database/mysql.md` 的条目理由与补充说明。

## 建表

| 规则 | 理由 |
|---|---|
| 自增 `bigint` 主键 | InnoDB 是索引组织表，自增主键让新数据顺序追加到末尾，避免页分裂；`int` 上限约 21 亿（无符号约 43 亿），大表会耗尽，`bigint` 与 Go 的 `int64` / `uint64` 对应 |
| `updated_at` 自动更新并建索引 | 用于增量同步、数据抽取和排查问题，由数据库维护，业务代码不需要写 |
| `utf8mb4` | MySQL 的 `utf8` 实际是 `utf8mb3`，最多 3 字节，存不了 emoji；`utf8mb4` 才对应 Go 字符串的 UTF-8 |
| `ROW_FORMAT=DYNAMIC` | 索引键前缀上限 3072 字节；`COMPACT` 只有 767 字节 |
| 不用外键 | 关联约束放在应用层，便于分库分表和在线变更，避免级联锁 |
| 单表不超过 40 个字段 | InnoDB 页为 16KB；行越小，一页容纳的行越多，读取同样行数所需的 I/O 越少 |
| 不先 `DROP` 后 `CREATE` | 在已有数据的环境执行会直接丢失数据 |

GORM 的 `AutoMigrate` 默认会创建外键，即使只在开发环境使用，也要设 `DisableForeignKeyConstraintWhenMigrating: true`。

## 字段

| 规则 | 理由 |
|---|---|
| `NOT NULL` + 默认值 | `NULL` 参与拼接结果为 `NULL`，`COUNT(col)` 不计 `NULL`，可空列的索引还要额外存储标记；Go 侧也省去 `sql.NullString` 之类的处理 |
| 主表不放 `TEXT` / `BLOB` | 大对象存在行外，读取要额外 I/O，占用 buffer pool，并拖慢主从复制 |
| `VARCHAR` 不超过 2000 | 索引长度按定义长度计算，而非实际长度 |
| 不改字段类型、不删字段 | 这类变更通常要重建表；在线变更需借助 gh-ost、pt-online-schema-change 或 8.0 的 `INSTANT` 算法，并评估锁表时间 |
| `DECIMAL` 存金额 | `FLOAT` / `DOUBLE` 是近似值，有精度损失；Go 侧用 `shopspring/decimal` 等类型或以最小单位存整数 |
| `TINYINT` 代替 `ENUM` | `ENUM` 增加取值要改表结构，排序按定义顺序而非字面值 |
| `datetime` 代替 `timestamp` | `timestamp` 上限为 2038-01-19；`datetime` 范围是 1000～9999 年。注意 `datetime` 不带时区，统一约定存 UTC 或固定时区 |

## 索引

- 二级索引的叶子节点存的是主键，主键越短，二级索引越小。
- 组合索引遵循最左前缀：`WHERE` 只用到后面的列时用不上索引。
- 冗余索引（如已有 `(a,b)` 再建 `(a)`）只增加写入成本。
- 前缀索引不适合需要排序或覆盖索引的场景；URL 这类前缀高度重复的字段，前缀索引的区分度很差，可改为存哈希列并建索引。

## SQL

| 规则 | 理由 |
|---|---|
| 不用 `SELECT *` | 无法使用覆盖索引，读取多余数据；表结构变化时还可能让扫描结果与结构体错位 |
| `WHERE` 字段不套函数、类型一致 | 函数和隐式类型转换都会让索引失效（8.0 可以建函数索引，但先考虑改写查询） |
| 不用前导通配符 `LIKE` | 不符合最左匹配，退化为全表扫描；需要全文检索时用 Elasticsearch 或全文索引 |
| 控制单条语句影响行数 | 主从复制在事务提交后才发送到从库，大事务直接转化为复制延迟；回滚耗时也与事务大小成正比 |
| 关联不超过两张表、少用子查询 | MySQL 的关联算法与优化器对复杂 SQL 支持有限，拆成多条简单查询更可预期 |
| 不用 hint | 数据分布变化后，固定的执行计划可能变成最差的计划 |
| 深分页改游标 | `LIMIT 100000,10` 要扫描并丢弃前 100000 行；`WHERE id > ? ORDER BY id LIMIT 10` 直接定位 |
| 统计语句走从库 | 大范围 `COUNT`、`SUM` 占用主库 I/O 与 buffer pool，影响在线写入 |
| `READ COMMITTED` | 相比默认的 `REPEATABLE READ` 减少间隙锁，降低死锁概率；需要可重复读的逻辑在应用层显式加锁 |
| 写操作幂等 | 网络超时后的重试、消息重复投递都会再次执行写操作；用唯一键、`INSERT ... ON DUPLICATE KEY UPDATE` 或带状态条件的 `UPDATE ... WHERE status = ?` 防止重复 |
| `UNION ALL` 优先 | `UNION` 会额外去重排序，确定没有重复时用 `UNION ALL` |

## MySQL 5.7 与 8.0 的差异

| 主题 | 5.7 | 8.0 |
|---|---|---|
| DDL | 不是原子操作，失败后可能残留中间状态，无法回滚 | 原子 DDL，但仍不在事务中回滚，变更前先备份 |
| 加列 | 需要重建或在线复制 | `ALGORITHM=INSTANT` 可秒级加列（不能用 `AFTER` 指定位置时才最快，8.0.29 起支持任意位置但仍建议追加） |
| 函数索引 | 不支持，`WHERE` 中对列使用函数必然全表扫描 | 支持函数索引（8.0.13+） |
| 多个 `ALTER` | 每次都要锁表或复制，必须合并 | 仍建议合并，减少元数据锁次数 |
| 默认字符集 | `latin1` | `utf8mb4` |
