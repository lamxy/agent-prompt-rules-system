# 保存模式

保存前讀完本檔案。交接文件的骨架是 `templates/HANDOFF.md` 與 `templates/GOTCHAS.md`。

## 第一步：記錄工作現況

工作到一半正是最需要交接的時候，因此未提交的變更不阻擋保存，而是要被記錄下來。

專案使用 git 時執行 `git status --short`。有未提交變更時，把變更檔案清單與「這些變更想做什麼、做到哪裡」寫入續作章節的「未提交的變更」小節；有 stash 或 WIP 分支時記錄其位置。不要求使用者先提交，也不因此中止保存。

專案不使用 git 時略過本步的版控指令，改為在交接文件中說明產出物的位置，並提醒使用者交接文件需要自行同步給接手者。

接著確認兩件事，這兩項不滿足時要先處理：

對話中的口頭決策是否已寫入檔案。使用者在對話裡確認過但只存在於對話中的決定，保存後就會遺失。逐項檢查本次工作中的決策，寫入專案文件或任務系統。

任務狀態是否已更新。完成的任務要標記完成，避免新會話重做。

## 第二步：偵測專案的任務管理方式

不預設任何工具。按以下順序偵測，命中且可用才停，工具存在但無法執行時繼續往下一層：

存在 `.taskmaster/` 且 `task-master` 指令可用時，使用 `task-master list` 與 `task-master show <id>` 取得結構化狀態。目錄存在不代表 CLI 已安裝，指令失敗時改讀 `.taskmaster/tasks/tasks.json`。

存在 `.planning/` 時讀取其中的 ROADMAP 或同類檔案。

存在 `TODO.md`、`ROADMAP.md` 或 `PLAN.md` 時直接讀取。

以上皆無且專案使用 git 時，從 `git log --oneline -20` 與分支名推導近期工作，並在交接文件中註明狀態為推導而非權威來源。

以上皆無且專案不使用 git 時，狀態改由使用者口述或從產出物的修改時間推斷，同樣註明為推導。此情況下交接文件的準確性完全依賴保存當下的記錄品質，應提醒使用者。

## 第三步：寫入交接文件

依 `templates/HANDOFF.md` 的骨架撰寫。內容必須具體到能直接執行，避免「持續進行中」一類無資訊的描述。

模板中的 frontmatter 鍵、各章節前的 `<!-- section: ... -->` 錨點、gotchas 節的 `<!-- block: ... -->` 錨點與 `<!-- on-demand -->` 停止標記不得刪除或改名，檢查工具依它們判斷結構；章節標題文字可依內容語言改寫。

寫作要求：所有路徑寫完整相對路徑；所有指令可直接複製執行；引用決策時指向來源檔案而非重述；狀態表反映實際檔案系統而非記憶。

專案已有權威的狀態文件時，例如 `CHANGELOG.md`、`.planning/` 或既有的狀態頁，交接文件不重複其內容，只做索引並補上那些文件沒有涵蓋的部分，主要是續作章節與本次工作的未提交變更。同一份狀態存在多處而無同步機制時，很快就會互相矛盾。

### 覆寫與刪除規則

交接文件只描述「現在」，不累積歷史。追加式寫法會讓文件無限變長，並讓新舊數字並存、互相矛盾。

1. **摘要每次覆寫**成三行（進度／停在／第一件事）。舊摘要不保留；需要留下的歷史寫進專案的決策記錄，沒有決策記錄的專案寫在提交訊息裡。
2. **已完成的列和項目要刪除，但先搬再刪，而且只刪能證明有去處的**：
   - 指向的節號用 grep 確認存在；commit 用 `git cat-file -e <hash>` 確認，其他倉庫的 commit 到那個倉庫核對。
   - 列中有「未實測」「未驗證」的片段，先搬到待處理事項，再刪該列。
   - 沒有其他來源的事實只能搬，不能刪。
   - 逐列判斷；以「已由其他列解決」為由刪除的，要寫明是哪一列。
   - git 歷史只算備份，不算另有來源。
3. **當前狀態**只列進行中、待開始、延後、待驗證的項目，另外最多保留 3 列最近完成、仍需核對的項目。**建議的下一步**只列未完成項目，每項標注「相關：G…」。
4. **已完成內容**只放關鍵檔案地圖，不寫版本號與測試數；這兩種數字放在權威來源（變更紀錄、測試輸出），交接文件寫了就會過期。
5. 待處理事項的指標寫 G<n> 或「檔案＋節號」，不寫「本文件某條」：條目搬動後這種指標會斷。

### 陷阱的分類

新陷阱先分類：

- 符合**核心約束**標準的，寫成一行放進核心約束，並附來源。標準：禁令、授權、跨倉庫寫入、隱私禁區、每次回報都會用到的使用者偏好，任一成立，而且沒有工具會擋下。核心約束不超過 10 行。
- 其餘放 `docs/handoff/GOTCHAS.md`，每條一個 `### G<n> 標題`，寫清楚現象、原因、做法；**同時**在觸發索引加一行「動作 → 一句話做法 → G<n>」。索引行本身就寫出做法，模型沒有去查 GOTCHAS.md 也能照做。編號只增不重用。

只寫現象會讓接手者重新排查一次，所以 GOTCHAS.md 的條目三者都要寫。範例：某個測試逾時失敗，原因是示範資料使查詢變慢而該測試會啟動外部程序，正確做法是執行測試前先清除示範資料而不是修改測試。

條目只有在「已有其他權威來源」或「確認失效」時才移出，並在決策記錄或提交訊息寫明去處。移出時索引行與 GOTCHAS 條目一起刪，否則 `check` 會 FAIL。

GOTCHAS.md 不存在而需要第一個條目時，依 `templates/GOTCHAS.md` 建立。

### 收尾

寫完後執行 `stamp` 寫入分支與 HEAD 錨點，不要手寫這兩個值。仍有待接手的工作時 `status` 為 `active`；工作全部完成且沒有下一步時用 `stamp --status closed`。

`check` 出現大小或格式的 WARN 時，先依上述規則收斂再提交。被中斷、需要緊急保存時可以先提交，並在摘要的「停在」註明「待收斂」。

## 第四步：建立入口

確保接手者找得到這份文件。專案有 `AGENTS.md`、`CLAUDE.md` 或同類入口檔時，在其中加入一行指向 `docs/handoff/HANDOFF.md`，並說明「接手既有工作時先讀此文件」。

判斷入口是否已存在，依據為檔案中是否已出現 `docs/handoff/HANDOFF.md` 這個路徑，不是比對句子措辭。那行可能由其他客戶端或先前的會話寫成，措辭未必與這次要寫的相同，比對句子會誤判為不存在而重複加一行。已存在時不重複加，也不改寫既有措辭。

專案沒有任何入口檔時，明確告知使用者交接文件的路徑，並詢問是否要建立最小的入口檔。不要靜默略過這一步，否則接手者不知道有這份文件。

入口建立後執行 `check`，通過後才進入下一步。

## 第五步：提交

專案使用 git 時，以 `docs: 更新進度交接` 或同等訊息提交，訊息語言跟隨內容語言。只提交 `docs/handoff/` 與本次為了交接而更新的入口檔，不順帶提交工作中的未完成變更。

同一次會話內既完成功能又要保存交接時，分兩次提交，功能在前、交接在後。交接提交只含交接文件與為交接而更新的入口檔，即使功能已完整驗證通過也不合併為單一提交。這樣 `git log -- docs/handoff/` 才是一條乾淨的狀態演進史；功能提交日後需要 revert 時，交接文件的更新也能獨立保留或獨立回退，不被連帶撤銷。

專案尚未安裝交接的 pre-commit 檢查時（`.git/hooks/pre-commit` 中沒有 `managed-by: handoff-check`），在首次提交前詢問使用者是否執行 `install-git-hook`。使用者拒絕時照常提交，之後的保存不再重複詢問，除非使用者主動提起。

pre-commit 檢查失敗時修正問題後重新提交，不得以 `--no-verify` 繞過。確需在交接提交中夾帶其他檔案時，向使用者說明原因，由使用者決定是否執行 `git config --add handoff.allow <路徑>`。

交接文件必須進版控，放在 `.gitignore` 的位置等於沒有交接。

專案不使用 git 時略過本步，並提醒使用者需要自行把交接文件同步給接手者。

## 交接文件的章節

依接手時的讀取順序排列。停止標記之前必讀，之後按需。

| 節 | 寫法 | 接手時 |
|---|---|---|
| 摘要 | 嚴格三行：進度／停在／第一件事；每次覆寫。讓接手者不讀全文也能判斷方向 | 必讀 |
| 當前狀態 | 表格；只列未完成項目，加最多 3 列仍需核對的近期完成項目 | 必讀 |
| 建議的下一步 | 具體到可以直接開始，說明前置條件是否已滿足；每項標注「相關：G…」 | 必讀 |
| 續作時必須知道的事 | ①核心約束（≤ 10 行，每行附來源）；②觸發索引（每行「動作 → 一句話做法 → G<n>」）；③未提交的變更 | 必讀 |
| 待處理事項 | 未決策的問題、已知但延後的缺陷、需要外部提供的資源、未驗證的片段；指向詳細記錄 | 按需 |
| 本機執行 | 啟動、測試、建置的完整指令與環境前置條件（語言版本、需先啟動的服務、需安裝的工具）。換機器或換客戶端時最常見的失敗點在前置條件。非程式碼專案改寫產出物如何預覽、校對或發布，或標為不適用 | 按需；中斷恢復時要用 |
| 已完成內容 | 關鍵檔案地圖，讓讀者能據此找到程式碼；不寫版本號與測試數 | 按需 |

保存當下有未提交變更時，「未提交的變更」小節必須記錄變更檔案清單、這些變更想達成什麼、以及做到哪一步；有 stash 或 WIP 分支時記錄其名稱與位置。半成品的脈絡遺失後，接手者往往選擇重做而非續作。

## 適合與不適合保存的時機

適合：一個任務或子任務完成之後；工作到一半需要中斷或切換客戶端時。後者是這個技能的主要用途，此時未提交的變更要被記錄而不是被排除。

不適合：產出物剛完成但尚未經使用者審核，因為審核意見還在對話中，保存後會遺失；使用者剛給了指示但尚未寫入文件；正在除錯且假設尚未驗證，此時記錄下來的推測會誤導接手者。

遇到不適合的情況時，先把缺的部分補進文件或任務系統，再執行保存，而不是拒絕保存。
