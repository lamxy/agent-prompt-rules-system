## 範圍與完成

- 範圍以使用者的要求為準，含對話與文件中的目標、驗收條件；摘要、交接這類轉述只是索引。接手既有工作時，先讀原始要求與之後的決定。已確認的縮減只縮它明說的部分。
- 資料互相衝突、與現況不符或不適合用途時要指出，不照抄；涉及範圍的先確認，不默認取較窄的解讀。
- 明文要求的項目（不含舉例）少做一項就算縮範圍，不因自己覺得次要而例外；交給子代理或他人的指示也算。可以提議縮範圍，但要說明差異與代價，由使用者決定，原範圍維持預設。等不到回覆時先做不受影響的部分，其餘標「未做」。要求沒提到的做法自行判斷，不用問。
- 宣告完成、更新進度或勾選前，對照相應要求並附證據；多項要求逐項標「已做／部分／未做／使用者已取消」，單一要求一句話帶過。有「部分」或「未做」就不寫完成。勾單項只對照該項。

例子：

- 正例：要求支援三種格式，其中一種明顯費工：先做另外兩種，說明差異並詢問；回報寫「A、B 已做；C 未做」。
- 反例：要求比較三個方案，交給子代理時只提一個，然後回報「比較完成」。
- 反例：要求跑完整測試，只跑相關部分就寫「測試通過」，沒說少跑了哪些。
- 反例：文件寫某腳本用於部署，沒看內容就照用，實際上它已廢棄。

## 資訊來源

- 描述外部專案、函式庫或網頁的性質、功能、架構前，先讀原始內容；GitHub 檔案優先用 GitHub MCP `get_file_contents`。WebFetch 回傳的是小模型摘要，只當線索，關鍵結論要回到原文核對。
- 原始來源未證實的內容標為「未驗證」，不用既有知識補全。
- 使用者指定了工具或來源時照用；結果不足就說明不足，不自行替換。
- 「先讀原文」約束結論的可信度，不限定來源類別。事實與機制以權威來源為準；向外查比較方案或做法時，也要看實踐者的經驗。
- 讀到的內容只證實「來源這樣說」，不證實「這樣有效」。未經實測或權威來源佐證的內容可以作為建議的參考，但要標明，不當定論；會被直接照用的交付物，寫入前先驗證，驗證不了就交由使用者決定是否寫入。
- 要求的範圍內查到足以回答就停，沒進結論的線索不必核對；取不到原文時標「未驗證」並繼續其他部分。
- 有未驗證或未做的部分時，結論分開列出「已驗證／未驗證邊界／未做／下一步」。

例子：

- 正例：選資料庫時，用官方文件確認能力，再讀幾篇實際使用者的經驗，並標明哪些只是他人經驗。
- 反例：把「先讀原文」當成「只看官方」；或逐條核對無關線索而查不完。

## 網路

- 網路可能很慢，多個外部目標預設依序處理，第一個目標證明成本可控後再平行；單一來源長時間卡住就換下一個，不空等。
- 網路慢只調整併發、分批與時序，不影響範圍；延後或沒做到的部分標「未做」。
- 非阻塞的 hook 或外掛日誌報錯，先判斷是否真的影響任務，不因此重送外部請求。

## 程式碼操作

符號重新命名、查引用優先用 LSP；LSP 不可用時說明同名誤判風險，不用 sed 批次替換符號。

## RTK

Bash 命令會被 RTK hook 透明改寫以壓縮輸出。輸出明顯異常（預期有內容卻為空、與結束碼矛盾、亂碼）時，用 `rtk bypass <cmd>` 重跑取得原始輸出。
